# eZ80 / Agon Light

`buildez80.py` targets the eZ80 in **ADL mode** — 24-bit registers, 24-bit
addressing, up to 16MB of address space. The reference platform is the
[Agon Light 2](https://www.thebyteattic.com/p/agon.html) / Console8 running MOS,
but the output is a plain ADL-mode binary and the only firmware calls it makes
are `RST 10h` (print a character) and `RST 08h` with `A=0` (`mos_getkey`).

```bash
python buildez80.py --model examples/guess/model.npz --output GUESS.bin
# or via the unified front end
python build.py --model examples/guess/model.npz --target ez80 --output GUESS.bin
```

Copy the `.bin` onto the SD card and run it by name from the MOS prompt.

## What changes, and why

Almost everything the Z80 build does is a workaround for 64KB. With 16MB those
workarounds stop paying for themselves:

| | Z80 (CP/M / ZX) | eZ80 (ADL) |
|---|---|---|
| Weight storage | 2 bits, 4 per byte | unrolled into code, or 1 byte each |
| Inner loop | unpack, rotate, mask, dispatch | one load and one add per weight |
| Accumulator | 16-bit, wraps | 24-bit, cannot wrap |
| Activations | 16-bit | 24-bit |
| Max layer width | 256 (DJNZ counts in `B`) | unlimited |
| Max model size | ~57KB total, weights included | ~508KB (see below) |

> **16MB of address space is not 16MB of RAM.** A shipping Agon has 512KB of
> SRAM at `0x040000`–`0x0BFFFF`, and MOS puts the stack at the top of it. That
> — not the 24-bit address space — is what bounds how large a model can be.
> `verify_artifacts.py` checks against it, and `--kernel auto` selects against
> it. The emulator has 8MB, so it will happily run an image no real machine
> could load; the check is what catches that.

The arithmetic is otherwise **identical**: same trigram hashing, same
`{-2,-1,0,+1}` weights, same `>>2` after each layer, same first-wins argmax.
A model trained and shipped for CP/M runs here unchanged.

### The accumulator is the interesting one

The Z80 sums each neuron in `HL`, so a large layer can overflow 16 bits and wrap.
The whole QAT overflow-penalty machinery in `libqat.py` exists to train models
that stay inside that range. In ADL mode `HL` is 24 bits and the sum simply
cannot wrap for any plausible layer width, so the eZ80 build is *more* accurate
than the Z80 build for exactly the models the penalty was fighting.

Where the Z80 would not have overflowed, the two produce byte-identical output —
`tests/test_ez80.py::test_ez80_and_z80_agree_when_the_accumulator_does_not_wrap`
checks this. `libinfer.forward(..., accum_bits=24)` models the eZ80 side.

### Layers wider than 256

`feedme.py` used to refuse hidden sizes above 255 because `DJNZ` counts in a
byte. No eZ80 kernel counts neurons in a byte, so there is no width limit:

```bash
python feedme.py --hidden-sizes 1024,512,256 --file training-data.txt
python buildez80.py --model command_model_autoreg.pt --output BIG.bin
```

`feedme.py` prints a note when a layer exceeds the Z80 limit, and the Z80
builders now raise a clear error rather than silently mis-assembling such a
model.

This claim did not used to hold for the **output** layer. `ARGMAX` counted
neurons in `B` and terminated with `DJNZ`, so a charset of 300 entries assembled
to `LD B,43` and picked the largest of the first 44 logits — no crash, no
warning, just the wrong character. `MAXI` and `RESULT` were single bytes too.
`ARGMAX` now walks `OUTBUF` with `SP` and stops by comparing against `OUTEND`,
with a 24-bit index and result; `tests/test_ez80_argmax.py` is the regression.
Byte immediates are also range-checked in the assembler now rather than masked,
so the mistake fails at assembly time instead of at inference time.

## Why reordering the sum is safe

Everything below rests on one fact, so it is worth stating plainly.

`libinfer.forward` computes `wrap(Σ wᵢⱼ·xⱼ + bᵢ, 24) >> 2`, and `wrap(v, 24)` is
exactly "the signed representative of `v mod 2²⁴`". Addition and subtraction mod
2²⁴ form an abelian group, so **any order or grouping of the addends produces the
same residue**, hence the same `wrap`, hence the same `>>2`. Splitting the sum by
weight sign, folding the bias in pre-negated, walking the weights input-major
instead of neuron-major — all bit-identical to the reference, not approximations
of it.

What may *not* move is the `>>2`. It floors, so it is a nonlinearity, not a scale
factor: `floor((a+b)/4) ≠ floor(a/4) + floor(b/4)`. It cannot be hoisted, folded
into the next layer, or applied to a partial sum.

## The three kernels

Pick with `--kernel`; the default `auto` takes the fastest one that fits in Agon
SRAM. All three are checked against `libinfer` *and* against each other in
`tests/test_ez80_kernels.py` — two independently generated programs producing a
byte-identical `OUTBUF` is the strongest signal available, and it needs no
reference model at all.

### `column` — unrolled, input-major (default)

The weights are ~73% zero, but the *activations* are sparser still: measured
over the shipped model, the input vector is ~10% nonzero and the hidden layers
16–39%. Counting only the weights actually reached, that is **8,192 of 37,865**
multiply-accumulates.

Row-major cannot exploit that, because which activations are zero changes with
every character emitted. Column-major can: each input gets a block meaning "this
input is nonzero, add its contribution everywhere it goes", and a layer runs only
the blocks its predecessor put on the active list.

```
CDRIVE1:  ld   hl,(iy+0)     ; next active column's block
          ld   de,3
          add  iy,de
          jp   (hl)
COL1_37:  ld   de,(INBUF+111)   ; x₃₇
          ld   hl,0
          or   a
          sbc  hl,de
          ld   (TMPV),hl
          ld   bc,(TMPV)        ; BC = -x₃₇
          ld   hl,(ACC+18)      ; per nonzero weight in this column:
          add  hl,de            ;   +1 -> add DE, -1 -> add BC, -2 -> twice
          ld   (ACC+18),hl
          ...
          jp   CDRIVE1
```

Accumulators move from a register into memory, costing a third instruction per
multiply-accumulate. Worth it when ~78% of columns are skipped outright.

Columns are dispatched as threaded code with `IY` walking a list of block
addresses. `SP` would be the obvious choice — `POP` reads a 24-bit word and
advances in one instruction — but then the list and the call stack alias each
other, and layer *n*'s epilogue would be building the list layer *n+1* is about
to consume through the same register. Two extra instructions per column buys an
intact stack, so `CALL`/`RET` stay usable and the per-neuron epilogue can be
shared instead of inlined 587 times.

Layer 1's list comes from an explicit scan of the input vector rather than from
`BUCKET_ADD` as it writes, because `BUCKET_ADD` can hit the same bucket twice and
a column listed twice would contribute twice.

### `row` — unrolled, weight-major

Every weight becomes code. In ADL mode `LD DE,(nnnnnn)` reaches any activation
anywhere in one 5-byte instruction, so a nonzero weight costs a load and an add,
and a zero weight costs nothing because it emits nothing.

```
w=+1:  ld   de,(ACT+3j)    ; ED 5B nn nn nn
       add  ix,de          ; DD 19
w=-1:  ld   de,(ACT+3j)
       add  hl,de          ; 19
w=-2:  ld   de,(ACT+3j)
       add  hl,de
       add  hl,de
```

`IX` sums the `+1` weights and `HL` the negative ones, so no per-weight sign
dispatch is needed; the bias is emitted pre-negated and folds into the negative
side for free. Then, because `>>2` floors, any negative accumulator ReLUs to
exactly zero — so a single `JP M` on the sign flag the `SBC` already set skips
the whole twelve-instruction shift chain. That path is taken by 60–75% of hidden
neurons.

### `compact` — the byte stream

The original kernel: one signed byte per weight, walked at runtime, neurons and
layers closed by sentinels. It visits every weight including the zeros, so it is
slow, but **its size does not depend on the model** — which makes it the only
option once a model is too large to unroll. That is the property the eZ80 port
exists for, so it stays.

```
LWT:  pop  de          ; DE = next activation, SP += 3
      ld   a,(bc)      ; A  = next weight
      inc  bc
      or   a
      jr   z,LWT       ; weight 0 - about 73% of a trained model
      jp   m,LNEG
      dec  a
      jr   nz,LEND     ; sentinel: end of neuron
      add  hl,de       ; weight +1
      jr   LWT
```

## Measured cost

`python bench.py --model examples/guess/model.npz --target com fast ez80`, for
the shipped 256→256→192→128→11 model, one generated character:

| target | size | instructions | speedup | Z80 T-states |
|---|---|---|---|---|
| `com` (packed) | 38,920 | 3,004,037 | — | 26,843,795 (6.7 s @ 4 MHz) |
| `fast` (index lists) | 43,520 | 319,515 | — | 1,992,905 (0.50 s @ 4 MHz) |
| `ez80-compact` | 146,626 | 923,194 | 1.0× | — |
| `ez80-row` | 251,997 | 90,340 | 10.2× | — |
| `ez80` (column) | 384,397 | 39,605 | 23.3× | — |

T-states are omitted for the eZ80 because its per-instruction timings differ
from the Z80's; comparing instruction counts is the honest measure. At 18.432 MHz
with the eZ80's much shorter memory cycles, the eZ80 build lands well ahead of
the fastest Z80 build in wall-clock terms.

Sizes leave 135KB (`guess`) and 122KB (`tinychat`) of Agon SRAM spare.

### What the earlier "known opportunity" got wrong

This document used to propose porting `buildfastz80com.py`'s index lists, for an
estimated threefold gain. That was the right diagnosis and the wrong remedy. An
index list still has to turn each index into an address, and the accumulator sits
in `HL`, so `LD DE,(HL)` is unavailable — the best data-driven form is 4–5
instructions per multiply-accumulate.

Unrolling is what the address space actually buys, and it is worth 10×, not 3×.
Skipping zero *activations* on top of that is worth another 2.3×. Neither needs a
weight stream at runtime at all.

## Emulation and testing

`libz80emu.Z80(adl=True)` implements ADL mode, and `libhost.AgonHost` provides
the two MOS entry points, so the eZ80 build is executed and checked against the
NumPy reference in CI just like the Z80 builds:

```bash
pytest tests/test_ez80.py tests/test_ez80_kernels.py \
       tests/test_ez80_argmax.py tests/test_ez80_emulator.py -v
```

The eZ80-only instructions the unrolled kernels use — `LD rr,(IX+d)` and
`LD (IX+d),rr` for `BC`/`DE`/`HL`, at `07`/`0F`/`17`/`1F`/`27`/`2F` under a `DD`
or `FD` prefix — are taken from the [published opcode
list](https://mdfs.net/Docs/Comp/eZ80/eZ80OpList) (Zilog UM0077 has the same
table), not from memory. `tests/test_ez80_emulator.py` covers them, including
that they stay inert outside ADL mode, where a plain Z80 would see `RLCA`/`RRCA`
with the prefix discarded.

**CI cannot catch an emulator that agrees with itself and disagrees with
hardware.** Before a release, boot `dist/GUESS.bin` in
[fab-agon-emulator](https://github.com/tomm/fab-agon-emulator) or on a real
machine; the binary carries the standard MOS ADL header (`"MOS"`, version 0,
ADL 1 at offset 0x40) and needs no special handling.
